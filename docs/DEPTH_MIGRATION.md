# Converting the engine to 2.5D

The engine moves the character along a single horizontal line. A beat-'em-up
needs a floor with depth: characters walk up and down as well as left and
right, pass in front of and behind each other, and only connect a punch when
they are standing at the same depth.

This document is the audit taken before that work started, and the plan it
produced. It is written against **e2f77ae**, with a clean tree. Every number
in section 4 was measured from the code and the art rather than estimated; if
you are reading this after the migration has begun, the sections describing
"today" are a snapshot and the code is the truth.

**Progress: stage 1 is done.** The character art is scaled to 96 px, the stage
is relaid out, and characters carry depth and height and move on the floor
plane. Stage 2, the depth sorting and the shadows, is next. Section 9 records
what has been decided and what is still open.

---

## 1. What the engine is

| | |
|---|---|
| SDK | ngdevkit, with its open source BIOS |
| Language | C99, `m68k-neogeo-elf-gcc`, `-O2 -fomit-frame-pointer` |
| Sound | Z80 via SDCC, ADPCM-A samples |
| Build | `gmake`; `Makefile` owns the assets, ngdevkit's `build.mk` the rest |
| Game code | `main.c`, 660 lines, plus `src/video.c`, `src/input.c`, `src/dialogue.c` |

No DATlib and no neodev: the game writes the sprite control registers itself.

The assets are generated by the Python tools in `tools/` and **committed** to
the tree. `make_stage.py` draws the stage procedurally, `gifs2sheet.py` and
`sheet2neo.py` build the character sheet, and both write the C headers the game
reads its sizes from. A change to a tool is therefore a change to the art, and
the regenerated files belong in the same commit — see risk 2 in section 8.

## 2. How position, movement and drawing work today

### Position

Four file-scope globals in `main.c`:

```c
static s16 hero_world_x = SCREEN_W / 2 - CHAR_W / 2;
static s16 camera_x = 0;
static s16 hero_y = GROUND_LEVEL;
static s16 hero_vy = 0;
```

Whole pixels, no fixed point. `hero_world_x` is a world coordinate;
**`hero_y` is a screen coordinate** — the top edge of the sprite, not a world
height — and that conflation is the single-plane model in one variable.

### Movement

All of it is in `update_hero()`, which also does the camera and the world wrap.
`WALK_SPEED` is 2 pixels a frame, added to `hero_world_x`. The jump integrates
`hero_vy` into `hero_y` and stops when it reaches `GROUND_LEVEL`, so the jump
arc and the floor position share an axis.

### Collision

**There is none.** No hitboxes, no overlap tests, and no enemies — the stage
contains one character. The collision system is entirely new code, which is
the one part of this migration with nothing to break.

### Sprite submission

The Neo Geo has no background layer, so everything on screen is a sprite, and
**draw order is sprite index** — a higher-numbered sprite draws in front. The
stage layers are numbered below the character for exactly that reason.

The character is a **sticky chain**. `init_hero()` sets bit 6 of SCB3 on its
second, third and fourth columns, which makes each inherit the leader's X, Y
*and height* and sit 16 pixels to its right. `move_hero_to()` then positions
all four with a single address write, by pointing `REG_VRAMMOD` at the stride
between SCB3 and SCB4 so one store lands in each. `set_frame()` rewrites all
56 SCB1 words every frame whether the frame changed or not, and mirrors by
both setting the H-flip bit and emitting the columns in reverse order.

One consequence of the sticky chain governs the whole y-sorting design:

> **An entity must occupy a contiguous, ascending block of sprite indices.**

So sorting by depth cannot mean shuffling entities' positions — draw order
follows the index, not the coordinate. It means choosing *which block* each
entity's tiles are written into. Section 6, stage 2 spells this out.

## 4. The sprite and scanline budget

Two hardware limits matter, and they are not the same limit:

| | |
|---|---|
| Sprites per frame | **381** |
| Sprites per scanline | **96** — the hardware drops the overflow |

A sprite is a 16-pixel-wide vertical strip up to 32 tiles tall, so width costs
sprites and height is nearly free. A 64-pixel-wide character is four sprites on
every scanline it touches, **including the scanlines where its art is
transparent** — the limit counts sprites present on the line, not pixels drawn.

### Today

Sprite indices: sky `1-20` (20, a sticky chain), hills `21-41` (21, one more
than the screen is wide so a column can cover the seam), ground `42-62` (21),
character `63-66` (4). **66 of 381 used**, 315 free. Sprite ROM is about 7%
full. Neither is a constraint.

Per-scanline occupancy is, and it is worst exactly where the floor goes:

| Scanlines | Sky | Hills | Ground | Character | Total |
|---|---|---|---|---|---|
| 0-79 | 20 | — | — | — | 20 |
| 80-111 | 20 | — | — | 4 | 24 |
| 112-175 | 20 | 21 | — | 4 | 45 |
| **176-191** | 20 | 21 | 21 | 4 | **66** |
| 192-223 | — | — | 21 | — | 21 |

Thirty sprites spare, and all three background layers stack up in the band the
fighting happens in.

### Worst case with six entities, on the stage art as it stands

Six entities crowded at the front of the floor (depth 48 and beyond), each
costing four sprites for its body and four for its shadow, on scanlines
176-191 where every background layer is present:

```
62 background + 24 bodies + 24 shadows = 110 / 96      over by 14
```

The hardware drops the overflow, and it drops the **highest-numbered** sprites
— which, after sorting by depth, are the frontmost entities. The failure mode
is the player's own character flickering out whenever a fight crowds the front
of the floor. This is an art layout problem rather than a code problem, and
flag C in section 5 is the fix.

### Worst case with the stage relaid out

With the floor band carried by the ground layer alone (flag C), and a
three-sprite shadow:

```
21 background + 24 bodies + 18 shadows = 63 / 96       33 spare
```

The busiest scanline in the frame then moves to around 120-127, where the sky
and hills meet the bodies reaching up out of the band, at **65 of 96**. That
leaves room for nine entities rather than six.

### The 68000 is not the problem

Six entities cost roughly 360 VRAM word writes a frame — 336 of them the tile
data, the rest positions — which is about 7,000 cycles including the per-column
address setup, against the roughly 30,000 cycles a vertical blank affords.
Insertion-sorting six mostly-sorted entities is a few hundred more. There is no
allocation anywhere in the design, and nothing that grows worse than linearly.

Sorting cost is a non-issue; the scanline limit is the real budget. That is why
section 6 puts the sprite audit last and the stage relayout second.

## 5. What conflicts with the model

### A. The character is 112 pixels tall, not 96

Measured from the art: the tallest frame is **99 px** and the widest **58 px**.
`sheet2neo.py` fits one bounding box to every frame of every animation, pads it
out to whole tiles and sits the art on the bottom edge, so the cell is 4x7
tiles — **64 x 112 px** — with the feet on the cell's bottom edge and 13 px of
transparent padding above the head. `HERO_TILES_H` is 7, and the height
submitted in SCB3 is 112.

The 96 in the specification is not arbitrary. It is `FLOOR_TOP - HUD_H`, or
128 - 32: the tallest character that clears a 32-line HUD when standing at the
back of the floor. And 96/99 of 58 px is **56 px** wide, which is the stated
bounding box. The intended art is this art scaled to 96 px; the build simply
never scales it. The `HERO=old` path does, through `prep_sheet.py --height`,
but the default `HERO=new` path has no scaling step at all.

**Fix:** give `gifs2sheet.py` a `--height` option using the same LANCZOS shrink
`prep_sheet.py` already has, and pass 96. `HERO_TILES_H` becomes exactly 6, every
constant in the specification becomes consistent, and a tile row of both sprite
ROM and scanline budget comes back.

Whatever happens, **`CHAR_H` must stay derived from `HERO_TILES_H`**. A literal
96 in the screen-Y derivation breaks silently the next time the art changes
size, and the symptom — a character floating a few pixels above its own shadow
— is a long way from the cause.

### B. Up is the jump button

`main.c:400` binds `CNT_UP` to jump, and the new model needs up and down for
depth. The jump has to move to a button. The genre convention is A to attack,
**B to jump**, the stick for all four directions of movement. This also changes
the hint text at `main.c:640-643`.

### C. The stage art has no floor in the walkable band

The walkable band is screen Y 128 to 199. Today that region is painted by the
**hills** layer, which sits at 112-191 and scrolls at a **quarter** of the
camera's speed, and the ground layer does not begin until 176. A character
standing at depth 0 to 47 would be standing on the distant parallax hills, and
the floor beneath its feet would slide at a different rate at the back of the
band than at the front.

The stage has to be regenerated. This layout puts the floor where the
characters walk, and is what brings the scanline budget back under the limit:

| Layer | Y | Rows | Covers | Scrolls | Sprites |
|---|---|---|---|---|---|
| Sky | 0 | 8 | 0-127 | never | 20 |
| Hills | 64 | 4 | 64-127 | quarter speed | 21 |
| Ground | 128 | 6 | 128-223 | full speed | 21 |

The walkable band is 128-199, with a 24-pixel apron at 200-223 below its front
edge, which gives the floor somewhere to read as receding. `draw_hills` needs
its three ridge baselines rescaled into a 64-pixel layer, and `draw_ground`
needs to draw a floor plane across the band rather than a flat-topped ground
line. It costs less sprite ROM than the current layout: 360 tiles against 400.

### D. `WORLD_WRAP` cannot coexist with camera bounds

`main.c:65` wraps the world every 1280 pixels, which is what lets the stage
scroll forever. Clamping the camera to stage bounds and locking it for a fight
room both require a stage that *has* ends. The wrap has to go.

This is safe for the parallax layers: `scroll_layer` already reduces its scroll
modulo one repeat of the artwork and handles negative values, so it never
depended on the wrap.

### E. A depth speed of 1.3 pixels a frame is not an integer

65% of `WALK_SPEED 2` is 1.3, and the engine moves in whole pixels, so the
depth speed can only be 1 or 2. The specification's ratio forces fixed point.

**8.8 fixed point**, with `x` as `s32` because stage widths run past the
±127 pixels an 8.8 `s16` can hold, and `z` and `air` as `s16` because a depth
of 71 is 18176 in 8.8 and fits comfortably:

```
X_SPEED   = 512     2.000 px
Z_SPEED   = 333     1.301 px        65% of X
DIAG_X    = 429     1.676 px        diagonal magnitude 1.999
DIAG_Z    = 279     1.090 px
```

The cheaper alternative is to keep integers and move depth by one pixel on two
of every three frames, which averages 0.667 — but it visibly jitters, and a
68000 adds 32-bit values in a single instruction, so the saving is not worth
the feel.

### F. "Decoupled from render" does not mean what it means elsewhere

On this hardware the frame clock **is** the vertical blank; there is no
independent render rate to decouple the logic from. The useful reading, and
what the plan implements, is that the logic pass touches no VRAM at all and a
separate emit pass does every VRAM write inside the blanking window. If a frame
overruns, the game slows down, which is what games of the era did. Keeping the
emit pass inside vblank is what the audit in stage 5 is really guarding.

### G. There are no enemies

Stages 2 through 5 cannot be tested with one entity: sorting by depth is
invisible, and collision has nothing to hit. A stationary training dummy goes
in during stage 1 so everything after it has something to test against.

### H. There is no shadow art, and no alpha to draw it with

The shadow is a new generated asset, 48 x 16, and it should be a **stippled**
dark ellipse rather than a solid one. The hardware has no blending; a 50%
checkerboard reads as a translucent shadow on a CRT where a solid blob reads as
a hole in the floor. Palette slot 4 is free — `video.h` allocates 0 to 3 for
text, hero, stage and UI.

### Two live bugs in the code being rewritten

**The character vanishes for the last 8 pixels of every fall.** `main.c:395`
sets `frame = 4` when the jump is within 8 pixels of the ground, but
`HERO_JUMP_FRAMES` is 4, so 4 is out of range. It indexes tile columns 16-19 of
the jump band, which are empty padding, and the character disappears until it
lands.

**The last frame of an animation lasts one game frame.** `advance_once` returns
"finished" as soon as the last frame is *reached* rather than after it has been
held for `rate` frames, so the attack is 22 frames long and not 24. Harmless
today, but that is the timeline the attack's active window is placed on in
stage 3, so it is worth correcting first.

### `ASSET_SPECS.md` has drifted

It documents the character as 64 x 64 in 4 x 4 tiles with a crouch animation.
That is the `HERO=old` path; the default `HERO=new` is 64 x 112 in 4 x 7 tiles,
with four jump frames borrowed from the run and no crouch at all. Stage 5
refreshes it.

## 6. The plan

Five stages. The build compiles and the game is playable at the end of each
one, and each is a commit.

### Stage 1 — the coordinate model — done

Add `src/floor.h`: `FLOOR_TOP`, `FLOOR_DEPTH`, the 8.8 helpers, and the single
derivation of screen Y from depth that everything else calls. Introduce the
entity:

```c
struct entity {
    s32 x;              /* world horizontal, 8.8 */
    s16 z;              /* depth on the floor plane, 8.8, clamped */
    s16 air;            /* height above the floor, 8.8; 0 is grounded */
    s16 vair;
    u8 facing, state, frame, tick;
};
```

as a `MAX_ENTITIES 8` array, still inside `main.c` — the file split comes later,
once the modules have earned their boundaries. Migrate movement to `(x, z)`
with the eight-direction speed table, delete `WORLD_WRAP` and add stage bounds,
move the jump to a button, scale the art to 96 px, and spawn the dummy.

Depth has no visual effect yet: the character moves up and down the plane and
nothing is sorted.

**Test by hand.** Walk in all eight directions. A diagonal must not cover
ground faster than a straight line. Depth must stop dead at both edges of the
band. A jump must land exactly on the floor from any depth, and the character
must not disappear at the end of it.

### Stage 2 — y-sorting and shadows

Regenerate the stage to the layout in flag C. Add `src/render.c`: insertion
sort the entity array by depth — it is almost always already sorted — then emit
the entity at rank *i* into the sprite block at `FIRST_SPRITE + i * 7`, three
sprites of shadow followed by four of body so the shadow draws behind its owner.
Keep a per-block cache of which entity, animation row, frame and facing it
currently holds, and skip the SCB1 rewrite when nothing about that rank changed;
depth order is stable most frames, so most blocks keep their contents.

A rank with no entity gets a height of zero on both chain leaders. The
followers inherit it, which is exactly how `show_stage` already switches the
sky off.

Generate the shadow asset.

**Test by hand.** Walk the character past the dummy: it must pass cleanly in
front when it is nearer and behind when it is further, with no flicker as they
cross. The shadow must stay pinned to the floor through a whole jump while the
body rises away from it. The title screen must still hide everything.

### Stage 3 — splitting collision in two

In `src/entity.c`, two separate systems:

**Body overlap** is an AABB in x and z only, with push-apart, so characters
cannot stand inside one another. Air is not consulted.

**Attack connection** needs all three of an x range in front of the attacker
(flipped by facing), a depth half-extent, and an overlap between the attack's
`[air_lo, air_hi]` band and the target's, so that a low attack misses an
airborne target.

The specification lists "x/z hitbox overlap" and "z alignment within a
tolerance" as two conditions, but on the depth axis they are the same test.
Folding the tolerance into the hitbox's depth half-extent gives one named
tunable per attack instead of two checks that can disagree:

```c
#define ATK_PUNCH_Z_TOL 10      /* the value the game lives or dies by */
```

It belongs in a per-attack struct so a punch, a kick and a jump attack can each
have their own, and so that tuning it is editing one named constant.

**Test by hand.** You cannot walk into the dummy from any direction. A punch
connects only when your feet are within about ten pixels of its depth, and one
pixel further out it whiffs. A grounded punch misses the dummy at the top of a
jump.

### Stage 4 — the camera and fight rooms

`src/camera.c` takes the dead zone out of the entity update and clamps it to the
current room's bounds. `src/room.c` holds the room table:

```c
struct room { s32 x_min, x_max; u8 z_min, z_max; u8 wave; };
```

The per-room depth limits are what let a stage narrow its floor for a bridge or
a corridor; the wave is what locks the camera and seals the exits until it is
cleared.

**Test by hand.** The camera stops at both ends of the stage. Walking into a
fight room locks it and seals the exit behind you. Clearing the wave releases
both. A narrowed room clamps depth tighter than the global band, at both edges.

### Stage 5 — the budget audit

Instrument the busiest scanline and check it against the 63 of 96 predicted in
section 4, with six entities crowded at the front of the floor. Confirm the emit
pass finishes inside the blanking window. Refresh `ASSET_SPECS.md`.

## 7. What the model requires, restated

For reference while implementing, since these are the numbers everything else
is derived from:

| | |
|---|---|
| Screen | 320 x 224, fixed, 4:3, no scaling |
| HUD | scanlines 0-31 |
| Floor band | 72 scanlines: depth 0 at screen Y 128, depth 71 at 199 |
| Sprite origin | the feet |
| Screen Y of the top | `FLOOR_TOP + z - air - CHAR_H` |
| Depth speed | 65% of horizontal; diagonals no faster than horizontal |
| Facing | left and right only, never up or down |

**Depth must not scale sprites.** No shrink registers, no per-depth size
change. Depth is expressed entirely through screen Y and draw order — which is
also why the sorting in stage 2 has to be right every single frame, with no
exceptions: it is the only thing creating the illusion.

## 8. The risky parts

1. **Stage 2's switch from one character to an entity array.** `set_frame`,
   `move_hero_to`, `init_hero`, `show_hero` and the title screen all assume
   `FIRST_SPRITE` *is* the character. This has to land in one commit; half
   migrated is not playable.

2. **Regenerating the stage shifts every sprite ROM tile offset**, because
   `HERO_TILE`, `SKY_TILE`, `HILLS_TILE` and `GROUND_TILE` — and `FIRST_SPRITE`
   — are all chained off the layers' tile counts. That chaining is what makes
   it safe. What is *not* safe is that the generated art is committed: the
   regenerated GIFs and `stage.h` must go in the same commit as the tool
   change, or the tree and the build disagree about where the tiles are.

3. **The fixed-point migration touches every movement site.** Do it in stage 1,
   while there is the least code to touch.

4. **The `HERO=old` path will not survive this.** Four-by-four tiles, a
   different height, and a crouch bound to down — which is now depth movement.
   Retiring the branch is the honest option.

---

## 9. Decisions

Settled, and built in stage 1:

1. **Jump is on button B**, and up and down steer through the floor's depth.
   Crouch went with it: down is depth now, and the current character had no
   crouch art in any case. (flag B)

2. **The character art is scaled to 96 px**, six whole tiles, rather than
   moving `FLOOR_TOP` down to 144. Moving it would have put the front row's
   feet at screen Y 215, inside the bottom sixteen lines that
   `ASSET_SPECS.md` warns fall outside a real TV's picture. (flag A)

3. **The stage is relaid out** into stacked layers. (flag C)

Still open:

4. **Retire `HERO=old`?** Nothing has been done to it. It still builds its
   sheet, but it is 4 x 4 tiles rather than 4 x 6 and its crouch animation is
   no longer reachable, so it is untested against the floor plane. (risk 4)

5. **A jump at the back of the floor clips the top of the head.** Found while
   verifying stage 1. At depth 0 the feet are on line 128 and the character is
   96 px tall, so a 45 px jump puts the top of the sprite at -13 and about 13
   rows are lost off the top of the screen.

   It is not a collision with the HUD - the HUD is on the fix layer, which
   draws over every sprite, so a jumping character correctly passes behind it.
   It is only the screen edge. Three ways out: leave it, since it is brief and
   only at the very back; lower the jump from 9 to 7, which peaks at 28 px and
   clears; or accept the head clipping as the cost of a floor that starts as
   high as it does. This is a question about how the jump should feel, so it
   is being left alone until the shadows are in and it can be judged properly.
